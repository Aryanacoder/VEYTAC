# VEYTAC — Demo rehearsal and release checklist

Version: 0.1.0 • Initial state: all items unchecked

## 1. Before recording

- [ ] Real expert/task and fallback are selected; no fictional factory access.
- [ ] Capture, external-processing, training, and publication permissions are separately recorded.
- [ ] No unauthorized people, confidential drawings, credentials, or unsafe work are in view.
- [ ] Phone camera/mic, HTTPS, charging, language, playback, and network are tested.
- [ ] The observer knows how to stop, defer questions, and revoke the question window.
- [ ] Current account balance and external Muse Code spend are reconciled; demo reserve is protected.
- [ ] The model/account is in the intended mode; no hidden mock provider.
- [ ] The demonstrator has not been given a script of supposedly spontaneous AI questions/answers.

## 2. Live demonstration sequence

1. Explain the real task and what ordinary recording fails to establish.
2. Start the phone capture and show its actual mode, timeline, and permission state.
3. Let the AI identify a relevant uncertainty; the observer opens a safe question window.
4. Obtain an actual answer. Show a correction or exception when it naturally occurs.
5. Display the proposed record beside the original evidence and approve its scope.
6. Present a held-out case or contrast; show correct application, clarification, or honest failure.
7. Preview the human lesson and validated dataset capabilities/missing fields.
8. Show robot-learning results only if actual run artifacts exist, with simulation labeling.
9. Show the private/public distinction and contributor approval before any publication.
10. Close with the future instrumented apprenticeship vision, separate from current capabilities.

A prerecorded fallback is acceptable when disclosed. A cached result must not be presented as new live reasoning. A staged safe task must not be presented as an operational factory deployment.

## 3. Claim wording audit

- [ ] “Live” is supported by a real capture/inference timeline.
- [ ] “Learns” specifies memory update or actual parameter training.
- [ ] “Expert knowledge” identifies demonstrator versus retrospective reviewer.
- [ ] “High quality” links to concrete quality checks and sample counts.
- [ ] “Robot-compatible” names the format, modalities, and loader validation.
- [ ] “Improves robot learning” links to a controlled result, not a video animation.
- [ ] “Simulation” means an executed supported model, not an illustration.
- [ ] “Multilingual” names languages actually tested, and distinguishes text from speech output.
- [ ] “Open source” applies to code; dataset/model rights remain independently documented.
- [ ] No claim of autonomous industrial safety, infinite retention, guaranteed impact, or guaranteed winning.

## 4. Repository release

- [ ] A clean checkout follows the documented setup path.
- [ ] Canonical schemas, mocks, runtime adapters, and evaluation commands are present and tested.
- [ ] `AGENTS.md` and setup docs reflect the actual implementation.
- [ ] Tests report actual results; blocked research jobs are not marked passed.
- [ ] No API key, access cookie, private recording, confidential document, or restricted dataset is committed.
- [ ] Source/model/data/asset licenses and attribution are recorded; newly authored code license is approved.
- [ ] Example data is permitted and labeled real, replayed, synthetic, or simulated.
- [ ] The founder's hackathon-period contributions are identifiable in history/documentation.
- [ ] Live calls are off by default in CI; optional GPU jobs are approval-gated.
- [ ] Unused cloud resources are stopped and cleanup confirmed.
- [ ] Claim inventory and actual verification reports are available to reviewers without exposing private sources.

## 5. Freeze and submission

The documented deadline is November 4, 2026, 21:00 Eastern / November 5, 11:00 Japan time. Re-check official organizer updates. Do not make optional feature work consume the submission buffer.

Record: final commit/tag, date/time, tested devices, model IDs, demo mode, dataset versions, open issues, core release status, and research evidence status. Submit only the claims supported by that frozen build.

## 6. Failure drill

- Provider unavailable: preserve recording and show capture-only/queued processing; use disclosed replay if needed.
- Bad transcription: correct it visibly and demonstrate revision propagation.
- Ambiguous observation: ask clarification or mark unknown; do not force an impressive answer.
- No robot improvement: show the actual limited/negative result and the next experiment.
- Budget exhausted: block paid processing; local review/export remains usable where already authorized.
- Permission withdrawn: stop and revoke access, even during the demo.

A credible response to failure is part of the startup-track product demonstration.
